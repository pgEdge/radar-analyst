# CLAUDE.md

Hard rules for every change in this repository. `CLAUDE.local.md`
holds machine-specific notes and is not committed.

## Context

pgEdge Radar Analyst reads a radar diagnostic archive, checks it
against deterministic rules, writes a brief per diagnostic category,
and serves the assessment over a JSON API with an Astro console.

- Deployment: docker-compose. Not published to PyPI or GitHub
  Releases. Internal service only.
- Dependencies: AI SDKs (`anthropic`, `google-genai`, `openai`,
  `ollama`) are REQUIRED runtime dependencies, NOT opt-in. The
  briefing step is the core value proposition here. The `openai`
  adapter (`ai/openai_compat.py`) also serves OpenAI-compatible
  endpoints via `OPENAI_BASE_URL`.

## Architecture

[ARCHITECTURE.md](ARCHITECTURE.md) carries the design in full:
layering, pipeline stages, adapter architecture, deferred work.
The rules that the code must not break are here.

- CRITICAL: Findings are deterministic. Only `rules/` may construct
  a `Finding`. Never emit an LLM-originated finding: reproducibility
  is the guarantee the word carries.
- CRITICAL: Verdicts survive an LLM outage. Every category verdict
  must be derivable from the worst finding severity alone, so an
  assessment always carries findings and verdicts even when every
  brief is missing. The severity floor in `orchestrate()` and
  `_analyze_db()` enforces this; `test_degraded_mode.py` pins it.
- The assessment's verdict is the worst of its category verdicts
  (`analyze/assessment.py::rollup_verdict`). `UNKNOWN` means
  uncollected and never outranks a verdict concluded from evidence.
- PostgreSQL access via `psycopg` v3 (async) with `sslmode=prefer`
  by default (matches radar libpq behaviour).
- All radar-analyst tables live in a dedicated `radar` schema (never
  `public`). All queries fully qualify: `radar.uploads`,
  `radar.jobs`, etc. Do not rely on `search_path`.
- Migrations are plain `.sql` files in `store/migrations/`, applied
  in lexical order at startup and tracked in
  `radar.schema_migrations`, so a newer build can open an older data
  directory and apply only what is missing.
- While pre-release there is one migration. A schema change edits
  `0001_init.sql` rather than adding a second file, because nothing
  deployed has data to preserve. Once something is deployed, a
  change gets its own file.

## Commands

- IMPORTANT: Run `run-ci-local.sh` before committing; it must exit 0.
- IMPORTANT: `run-ci-local.sh` writes `ci-<timestamp>.log` in the
  repo root; never leave more than the most recent one behind,
  delete the older ones.
- Local CI script: `run-ci-local.sh` (lint, type check, unit tests,
  web lint and tests, Astro build, wheel build, Docker build, e2e in
  Docker).
- Integration test script: `test-radar-analyst.sh` (runs against the
  docker-compose stack; full upload → parse → assess → retrieve flow
  against a radar-format fixture generated by
  `src/radar_analyst/tests/make_sample_zip.py`).
- `Makefile` wraps the above: `make lint`, `make typecheck`,
  `make test`, `make e2e`, `make ci`, `make matrix`, `make docs`,
  `make notice`.
- Tests run against the pgEdge PostgreSQL image, never upstream
  `postgres`. `RADAR_ANALYST_PG_MAJOR` selects the major and
  defaults to 18; CI runs 16, 17, and 18.

## Testing

- CRITICAL: Test-Driven Development is a HARD REQUIREMENT. Every new
  function, class, or module begins with a failing test. No
  exceptions, including wiring and glue code. Every commit includes
  tests for the code it touches.
- Tests live in `src/radar_analyst/tests/`; plain `def test_*()`
  functions (no test classes).

## Code style

- IMPORTANT: Always run `flake8` (via `src/radar_analyst/flake.sh`:
  `--ignore F722,W503 --max-line-length=79 --max-complexity=8`)
  before committing Python code. No auto-formatter: write code that
  complies with flake8.
- KISS, DRY, stdlib-first, explicit error handling at system
  boundaries.

## Documentation

- IMPORTANT: As you implement functionality, update the
  documentation in README.md and docs/index.md.
- CRITICAL: Documentation structure:
  - README.md: Developer-focused (building, contributing, running
    locally, full technical details)
  - docs/index.md: User-focused ONLY (deploying via docker-compose,
    pointing at a Postgres, uploading a zip)
  - ARCHITECTURE.md: Engineering design: layering, decisions,
    trade-offs. Update in the same PR as the structural change it
    describes (see §13 of the doc itself for the ownership rules).
  - These files must be kept in sync for shared content
    (requirements, usage examples, etc.)
  - docs/LICENCE.md must exist (copy of root LICENCE) for MkDocs
    navigation
  - NO docs/contributing.md or docs/code-of-conduct.md (developer
    content stays in root only)
- Changelog: `## Added` / `## Changed` / `## Fixed` internal
  changelog style. Only user-facing changes. `## Fixed` is for bugs
  from a prior tag, not same-cycle churn.

## Vocabulary

- CRITICAL: Vocabulary is fixed. Input = **radar archive**; complete
  result = **assessment**; deterministic issue = **finding**;
  category health = **verdict** (`HEALTHY`/`WARNING`/`CRITICAL`);
  per-category narrative = **brief**; rendered output = **report**;
  the Astro GUI = **the console**. Product name is *pgEdge Radar
  Analyst* or *radar-analyst*, "the analyst" in running prose; never
  *pgEdge Radar-Analyst*, never "Radar Analyst" standalone. The
  collector is *radar* or *pgEdge Radar*. Never "archive" as a verb
  (say *retained assessments*, *assessment history*). No AI
  vocabulary in customer-facing text.
- Internal glossary is separate: rules, rule modules, facts,
  parsers, and snapshots are internal terms. The ten rule modules
  are NOT the five briefing categories.

## Git and review

- NEVER include Co-Authored-By or any Claude/AI attribution in
  commit messages.
- Commit messages should be short, one-line, imperative. No "chore:"
  prefix: use `fix:`, `feat:`, `build:`, `deps:`, `refactor:`,
  `test:`, `docs:` or a plain verb. Example: "feat: add POST
  /api/uploads endpoint".
- No verbose multi-paragraph commit messages.
- NEVER use `git checkout` or `git restore` on files with
  uncommitted changes: use Edit tool to modify only the specific
  lines instead.
- CRITICAL: NEVER overwrite or delete ANY files without checking if
  they are committed or backed up.
- CRITICAL: NEVER use the word "release" in git tag names (use
  version number only, e.g., "v0.1.0" not "Release v0.1.0"). Tags
  exist only for internal version tracking; this is not a public
  distribution.
- All changes go through PRs: no direct commits to main once the
  repo is shared.
- PRs require at least one peer review before merge.
- CI (flake8, ruff, mypy, pyright, pytest, web checks, Docker build
  + e2e) must pass before merge, on PostgreSQL 16, 17, and 18.
- Branch protection on main once shared.
